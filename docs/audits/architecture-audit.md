## 2. Code quality

De facto conventions observed in the cleanest/newest files (`pipeline_common/triangulation.py`, `Mapping/estimate_symmetry_no_mesh.py`, `pipeline_common/view_selection.py`): `from __future__ import annotations`, full type hints on every function signature, module docstring explaining purpose + cross-references to design docs + "migrated from X" provenance, stdlib imports → third-party → local (`pipeline_common.*`) import blocks, and Google/NumPy-lite one-line-summary docstrings on every public function.

| File | Issue | Severity |
|---|---|---|
| `Mapping/evaluate.py` | 1376 lines, mixes CLI argument parsing, single-run scoring, bulk `--all` orchestration, a `_MeshCache` class, and metric definitions (AUC, precision@θ, SDE_ref, F1_ref/F1_ref_hungarian) in one file. No internal section separation beyond comments. | Medium |
| `Mapping/estimate_symmetry.py` (613 lines) vs `Mapping/estimate_symmetry_no_mesh.py` (521 lines) | The no-mesh version has `from __future__ import annotations` and consistently typed signatures; spot checks of `estimate_symmetry.py` show partial typing (present on some functions, absent on others) — the two "parallel" estimator files don't share a consistent typing standard even though they're conceptually siblings. | Low |
| `MolmoPointing/molmo_multiview_runner.py` | 1186 lines, single file covering model loading, three prompting "flows" (a/b/c), per-object view selection, JSON I/O, and CLI — the file's own docstring (lines ~40-50) enumerates the three flows, confirming it's intentionally one multi-mode entrypoint rather than an accidental grab-bag, but it is still a mixed-responsibility file by line count and function count. | Low |
| `Mapping/audit_view_indices.py` | Superseded by `audit_view_indices_v2.py` per the v2 docstring itself ("Version más completa de audit_view_indices.py"), yet v1 is still present, unmarked as deprecated, importable, and would give an outdated/incomplete audit if run today. | Medium |
| `Mapping/check_origin_compactness.py` | Superseded by `check_origin_full.py` per that file's own docstring ("Versión 'población completa' de check_origin_compactness.py"). Same live-but-obsolete pattern as above. | Medium |
| Root-level `.sh` scripts (`cleanup_all_experiments.sh`, `find_extra_renders.sh`) | No `set -e`/error handling visible at a glance from filenames alone; not reviewed line-by-line here but flagged because they sit outside the Python type-hint/docstring convention entirely and aren't mentioned in `CLAUDE.md`. | Low |

No missing-docstring problem was found in the core pipeline scripts or `pipeline_common/` — every file sampled had a substantive module docstring. Import order was consistent (stdlib/third-party/local) everywhere sampled, including the messier one-off scripts.

## 4. Reproducibility issues

- **No hardcoded Windows/Unix absolute paths found** in any `.py` or `.ipynb` file (repo-wide grep for `C:\Users`, `/Users/`, `/home/pespinoz`, `/mnt/`, `Desktop` matched nothing outside `venv/`). All path-taking scripts consistently use `argparse` with `--renders-root`/`--objects-root`/`--results-dir` style flags. This is a genuine strength, not a gap.
- `environment.yml` pins a Linux/CUDA build (`prefix: /home/pespinoz/miniconda3/envs/tesis_env`, `nvidia-*-cu12` wheels, `pytorch3d==...+pt2.6.0cu124`) — consistent with CLAUDE.md's statement that GPU/Molmo2 steps only run on the remote server, not locally on Windows. Not a bug, but worth noting explicitly in `README.md`'s installation section that this file is Linux/CUDA-specific and won't install as-is on the Windows dev machine (the section wasn't fully read for cross-check here, so this is a "verify README says this" flag, not a confirmed omission).
- **`gpytoolbox`, `rtree`, `scikit-learn` are referenced by name in `CLAUDE.md`** ("`gpytoolbox`/`rtree` para `evaluate.py --with-reference-metrics`/`--all`", "`scikit-learn` para HDBSCAN") but none of the three appear in `environment.yml`'s pip list. Either the env file is incomplete/stale relative to actual imports, or these are installed via an undocumented secondary step — worth resolving, since `evaluate.py --all` (the bulk/paper-metrics path) would fail on a fresh `environment.yml` install.
- **Random seeds**: usage is deliberate and documented, not ad hoc. `pipeline_common/view_selection.py` derives a per-object deterministic seed (`md5(object_id) mod 2**31`) rather than one global seed, with an explicit rationale in its docstring; `Mapping/evaluate.py` exposes `--ref-seed` (default `SDE_REF_SEED_DEFAULT`, `-1` to disable) for `gpytoolbox`'s surface sampler; `Mapping/check_origin_compactness.py` takes its own `--seed` (default `0`) via stdlib `random`. Three different seeding mechanisms across three files is not wrong given their different purposes (deterministic per-object view choice vs. reproducible surface sampling vs. a standalone diagnostic script), but it does mean "the seed" is not a single global concept — a reader trying to reproduce one exact evaluation run needs to know which of the three applies.
- Undocumented assumed data files: several `Mapping/check_*.py` scripts (`check_sde_vs_angular.py`, `check_origin_compactness.py`, `check_origin_full.py`) take `eval_*_results.json` files produced by prior `evaluate.py` runs as required input, referenced by example paths in their own docstrings (e.g. `eval_s224_flat_plane_v04_1_ransac_svd_sde_results.json`) rather than by a documented naming-convention spec — the convention is inferable from `pipeline_common/naming.py` but isn't cross-referenced from these scripts' docstrings.

## 5. Structural problems

- **True duplicated/superseded pairs** (not independent tools — one explicitly supersedes the other per its own docstring):
  - `Mapping/audit_view_indices.py` → superseded by `Mapping/audit_view_indices_v2.py`.
  - `Mapping/check_origin_compactness.py` → superseded by `Mapping/check_origin_full.py` (full-population version).
- **Related but distinct** (not duplicates, despite similar names/domains — confirmed by reading their docstrings): `check_independent_vs_midpoint.py` (compares `--point-mode independent` vs `midpoint`) and `check_sde_vs_angular.py` (correlates SDE vs. angular error) answer different research questions and both feed `check_origin_compactness.py`/`check_origin_full.py` in a documented pipeline (`check_sde_vs_angular.py` → CSV → `check_origin_compactness.py`/`check_origin_full.py`). This is a legitimate ad hoc analysis chain, not redundancy — but it exists entirely outside `pipeline_common/` and `evaluate.py`, so its logic (reading `eval_*_results.json`, computing Pearson/Spearman correlations) isn't available to any future script without copy-paste.
- **Visualization duplication across three scripts**: `Mapping/visualize_rays.py`, `Mapping/visualize_symmetry.py`, and `Mapping/export_symmetry_overlay.py`/`render_symmetry_comparison.py` all independently define the same GT/predicted color convention (blue/green/red/magenta), stated verbatim in multiple docstrings ("Colors match the Polyscope debug viewer... GT axis: blue (0.15, 0.40, 0.90)..."). This is a real case of copy-pasted constants that belong in one shared module (e.g. `pipeline_common/viz_colors.py`) rather than four docstring-and-code copies.
- **`InteractiveViewer/view_symmetries.py` vs `Mapping/visualize_symmetry.py`**: both are Polyscope-based interactive viewers of an object plus symmetry overlay, living in two different top-level directories. Not fully verified line-by-line here, but the naming and stated purpose overlap enough that it's worth confirming whether `InteractiveViewer/` is a predecessor of the now-more-featureful `Mapping/visualize_symmetry.py` (which additionally supports GT vs. predicted comparison) rather than a distinct tool.
- **Mixed-responsibility scripts**: `Mapping/evaluate.py` (§2) and `MolmoPointing/molmo_multiview_runner.py` (§2) are the two largest, most multi-purpose files in the repo; both are internally documented well enough to navigate, but neither is split along stage boundaries the way `pipeline_common/` is.
- **Abandoned/leftover experiment files**: none found as tracked `.py`/`.ipynb` — the git status snapshot at the start of this session shows several already-deleted artifacts (`analisis_tiempos_postprocesamiento.ipynb`, `audit_view_indices_analysis.ipynb`, `audit_view_indices_raw.csv`, `audit_view_indices_summary.csv`, `log_postprocesos*.txt`, `postprocesos_console.log`, `reference_metrics_axis_all.csv`, `reference_metrics_plane_all.csv`, `scratch/*.csv`) — i.e. this cleanup is already underway on the `refactor` branch, not a gap this audit needs to flag as new work.

## 6. Experiment and results organization

- Results are stored alongside inputs under a per-object convention: `<renders_root>/<symmetry_type>/<object_id>/<size>/<lighting>/`, holding accumulative JSONs (`molmo_multiview*.json`, `mapped_points_3d*.json`, `predicted_symmetry*.json`, `eval_*_results.json`) — documented in `CLAUDE.md`. This is a deliberate, consistent, code-adjacent-but-not-code-mixed layout (results live under a separate `renders_root`/`objects_root`, not inside `Mapping/` or `MolmoPointing/`), which is good practice.
- `pipeline_common/naming.py` (26 lines) centralizes the `--experiment-id` filename-suffixing convention, so traceability from a script invocation to its output filename is enforced by shared code rather than by each script reimplementing suffix logic — this is a strength, confirmed by `Mapping/run_all_postprocessing.py`'s docstring referencing "File isolation guarantee" in `MolmoPointing/Experiments.md`.
- `Mapping/export_viz_samples.py` explicitly generates a `README.md` per results export with the exact `visualize_rays.py` commands used — a good, if manual, traceability mechanism from a result back to the command that produced its visualization.
- Weak point: the diagnostic-script outputs (`check_sde_vs_angular.py`'s discordant-objects CSV, etc.) are not written into the same `<renders_root>/...` convention — they're ad hoc CSVs passed by explicit path between scripts (consistent with the already-deleted `scratch/*.csv` files seen in git status), so this class of output has no consistent home and depends on the user remembering to pass the right path to the next script in the chain.
- `results*`, `Tesis_DCC_MDS`, `Prompted_*`, `experiments_17*`, `Gemini_poster_theme` are all gitignored — bulk experiment outputs are correctly kept out of version control.

## 7. Documentation gaps

- `README.md`'s repository-structure tree is stale (§1): missing `pipeline_common/triangulation.py`, `Mapping/estimate_symmetry_no_mesh.py`, all `Mapping/` one-off scripts, and the `docs/` directory's six files. Anyone onboarding from `README.md` alone would not discover the mesh-free pipeline exists.
- No docstring/README gaps were found in the core pipeline modules or `pipeline_common/` — module- and function-level docstrings are present and substantive throughout every file sampled.
- Undocumented data schema: the exact JSON schema for `molmo_multiview*.json`, `mapped_points_3d*.json`, `predicted_symmetry*.json`, and `eval_*_results.json` is not collected in one place — it's reconstructable from scattered docstrings (e.g. `estimate_symmetry_no_mesh.py`'s "Output" section shows one method's dict shape) but there's no single schema reference a new script author could check before reading/writing these files.
- The eight tracked root-level scratch documents (§1) have no explanatory note anywhere (not in `README.md`, not in `CLAUDE.md`) about whether they're historical records worth keeping or leftover working notes — their status is genuinely ambiguous from the repo alone.
